    RTEMS 6 on the Zynq-7000 of the PYNQ-Z2¶

    The rtems6-zynq7000-pynqz2 platform targets the Zynq-7000, a system-on-chip with two Arm Cortex-A9 cores and programmable logic, running RTEMS 6 on the PYNQ-Z2 board. RTEMS is built there in its single-processor configuration, so the application runs on the core 0. It is built with arm-rtems6-gcc, of the RTEMS Source Builder, and the program is loaded into the DDR memory of the board. The platform maps the addresses from 0x40000000 to 0xC0000000, the M_AXI_GP0 and M_AXI_GP1 windows through which the processor reaches the programmable logic, as device memory, so a fixed-location field placed there reaches an IP of the design.

    The servers on the host¶

    The board is debugged with hw_server, of AMD Vitis, which runs on the host and serves both the GDB server of the core 0, at port 3000, and the connection of XSDB, the debugger of Vitis, at port 3121:

    $ hw_server -s tcp::3121

    Preparing the board¶

    The processing system of the Zynq needs its clocks, its DDR memory and its pins initialized before a program runs, and the programmable logic needs the bitstream of the hardware design. Both depend on the hardware design of the project, so the project carries a Tcl script that does it, next to the ps7_init.tcl that Vivado exports for the design and to the bitstream, and names it with xsdb-init in the app section of termina.yaml:

    app:
  platform: rtems6-zynq7000-pynqz2
  profile: debug
  xsdb-init: assets/xsdb/init.tcl

    A test inherits the script of app when it runs on the platform of the application. A test of a library, or one that needs another script, gives its own with xsdb-init in its entry of the tests: section, as a map from the platform to the path, in the same way as linker-script. The content of the script depends on the design. The following one is an example for a project that keeps the files exported by Vivado under assets/: it resets the system, initializes the processing system, configures the programmable logic with the bitstream, and leaves the core 0 halted:

    connect -url tcp:localhost:3121
targets -set -nocase -filter {name =~ "APU*"}
rst -system
after 1000
targets -set -nocase -filter {name =~ "APU*"}
source assets/xsdb/ps7_init.tcl
ps7_init
fpga -file assets/bitstream/design.bit
ps7_post_config
targets -set -nocase -filter {name =~ "*A9*#0"}
catch {stop}
disconnect

    Vivado exports ps7_init.tcl with the hardware of the design, in the .xsa file that File → Export → Export Hardware writes, which is a ZIP archive. The script sets the clocks, the DDR controller and the pins of the processing system as the design configures them. A project with no logic of its own in the programmable logic still needs it, exported from a design that contains only the processing system, and its script leaves out the fpga command.

    A program loaded without this reset starts from the state that the previous one left in the processor, with its MMU and caches enabled, and RTEMS fails to start over it. The script is therefore run before every session and every run of a test.

    Debugging¶

    A debugging session from Visual Studio Code first asks the XSDB command server described in the next section to run the script of xsdb-init, then connects the debugger to the GDB server at port 3000, as the Debugging chapter describes, and load writes the program into the DDR memory. A session from the command line runs the script on the host from the root of the project before connecting gdb-multiarch:

    $ xsdb assets/xsdb/init.tcl

    Running tests¶

    The runner of termina test cannot run XSDB itself when it works inside the container, since XSDB is part of Vitis and runs on the host. It asks an XSDB command server on the host to run the script before each run of a test, and before each case with --isolated. The server is started from the root of the project, since the script and the paths it uses are relative to it:

    $ cd my-project
$ xsdb -eval "xsdbserver start -port 3122; vwait forever"

    The runner reaches the server at the host of the GDB server and at port 3122, and the option --xsdb gives another host or port. A test without a script in xsdb-init, or whose server does not answer, is reported as invalid. From the container, port 3122 has to be allowed on the docker0 bridge along with the GDB servers, as the Debugging chapter shows.
